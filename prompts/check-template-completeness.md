# Check the deployable TADp template against the protocol

Work in the TADp reference repository. Compare the binding protocol with its
reusable template and establish whether the template supplies everything an
adopting project needs. Creating or reading this prompt does not execute it.
Execute it only on a human's instruction. Report findings in the response;
do not create protocol-development documents or copy development records into
the template.

## Authority and boundary

Read root `AGENTS.md`, [repository prompt instructions](AGENTS.md),
`protocol/AGENTS.md`, the
[suite index](../protocol/evidence/authoritative/LLM/00_Codex_Invariant_Suite_Index.md),
and every applicable specification. Apply
[specification 11](../protocol/evidence/authoritative/LLM/11_Codex_Prompt_Keyword_Specification.md)
to the invocation; references, inventories and examples are inert.

This is a completeness check, not permission to revise protected sources.
The only recording exception is the suite's existing authority to append
directly evidenced factual invariant conflicts to their required registers;
it grants no resolution or invariant-revision authority. Disclose those paths.
Read the protocol as authority and the template as the object being checked.
Do not change invariants, reusable sources, locks, edit guards, adoption,
accepted or closed claims, or live project records. Present exact proposed
template corrections and required authority for separately authorized work.
Do not execute linked maintenance prompts or expand into a documentation
refresh. The example repository and `_old/` are outside the target.

Only template-related artifacts belong in a deployable package: reusable
record shapes, scaffold instructions and navigation, the governing runtime
suite, operational workflow prompts, and necessary runtime tools and hooks.
Classify supporting assets by their actual use, not just their extension or
directory. Do not copy protocol-development initiatives, products, realizations,
maintenance reports, release-planning records, historical development decisions,
or development-only documentation. Preserve source identity by citation when
an excluded source is referenced; report an unresolved dependency rather than
copying it, removing its link, or rewriting its authority.

## Procedure

The numbered actions are serial. Tables and coverage inventories are reference
material, not parallel action lists.

1. **Capture the baseline.** Discover the Git root, branch, commit, status,
   staged/unstaged/untracked changes, directory instructions and ignore rules.
   Preserve unrelated work. Inspect existing verification entry points and run
   the read-only protection check and validator from `protocol/`, using the
   configured interpreter. Separate baseline findings from audit discoveries.
   Do not refresh a lock to absorb existing drift.

2. **Derive requirements from authority.** Read the applicable suite before
   consulting templates or development clues. Inventory every required record,
   embedded section, conditional record, response shape, prerequisite and
   consuming stage. Include project setup, evidence and conflicts, realization
   provenance, scope/initiative allocation, all initiative types, decisions,
   acceptance, execution/delivery, completion/coherence, reopening, Git placement,
   integration and separate scope closure. Include proposed and partial effort
   when assessing coherence without promoting its standing. Preserve the human
   gates and closed-claim protections of specifications 07, 09 and 10.

3. **Compare actual coverage.** Inspect
   [TEMPLATE-COVERAGE.md](../protocol/template/TEMPLATE-COVERAGE.md) and its
   machine-readable rows against the requirements and actual files. Do not
   treat a `covered` label or passing structural check as semantic proof.
   For each requirement record the exact governing locator, reusable source
   and section, kind, applicability/trigger, owning activity, destination,
   required inputs/fields, verification and disposition. Detect omitted fields,
   competing shapes, stale paths, wrong ownership, unsafe destinations and
   unjustified universal obligations. Keep embedded sections in their owner;
   Stage 9 readiness remains a response unless a governing rule requires a file.
   Check all fourteen numbered workflow prompts, their prerequisite declarations,
   the shared contract and scope closure against the same map.

4. **Check the deployment boundary and dependency closure.** Inventory
   `protocol/template/project/`, the full reusable `protocol/template/` library,
   runtime suite, tools, imports and hooks. Trace adoption instructions and
   relative links at both source and installed destination depth. Identify
   necessary assets absent from the template and dependencies on excluded
   development records. Do not assume copying all of `protocol/` is an adoption
   strategy. Review initial installation and later synchronization separately:
   existing project instructions, customized records, user prompts, initiatives,
   products, evidence and local work must survive. Installing newer sources is
   not adoption, migration, acceptance, reopening or completion.

5. **Verify without altering the project.** Inspect commands before execution.
   Use read-only checks or disposable, isolated fixtures outside protected
   trees for copying and installation experiments. Test actual destination
   paths, links, imports, required hidden files, source identity and unchanged
   locks. Do not populate fictional project decisions or create durable
   development reports. Run existing relevant regression tests and disclose
   failed, skipped and unperformed checks. Do not change a validator or lock
   just to make the audit pass.

6. **Review and report.** Reconcile the requirement inventory with every
   finding and inspected template asset. Give dispositions of covered,
   conditional with reason, missing, incomplete, excluded development material,
   or blocked by exact authority/evidence. Supply the smallest precise
   template-only correction proposal for each gap. Confirm the final Git diff
   contains only mandatory factual conflict entries, if any, distinguishing
   independently changing user work. Otherwise keep the audit read-only.
   Report directly evidenced invariant contradictions through the
   governing conflict procedure; this prompt cannot authorize their resolution.

## Completion response

Return the coverage matrix, deployment asset inventory, exact missing sources
or fields, excluded dependencies, proposed template corrections, required
authority and verification commands with roots and exit results. State the
reviewed revision and limits. Do not claim completeness while required assets,
links or dependencies remain unresolved. Confirm that no protocol-development
documents were created or copied and no example synchronization occurred.
