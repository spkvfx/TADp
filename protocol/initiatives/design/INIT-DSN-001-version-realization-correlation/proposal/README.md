## Precedence

1. Current applicable authoritative evidence remains binding until an accepted
   authorized successor revision becomes effective.
2. The User's exact invariant-revision authority permits the named change and
   protected edits but does not infer initiative acceptance or completion.
3. Accepted initiative decisions, once recorded, govern this initiative's
   bounded design.
4. The proposal, realization suite, example migration case, observed Git
   history, and recommendations remain contextual or proposed.

When sources conflict, preserve both identities and use the authoritative
conflict or human-decision procedure. Recency, a version token, or implemented
behavior does not increase evidence authority.

## Source handling

- Keep the realization note, suite index, and proposal history traceable.
- Add a revision or receipt instead of overwriting an exact human response.
- Record source, standing, date, scope, and limitations for every material
  claim.
- Keep credentials, generated exports, and unrelated working files out.
- Link every material correction to an assumption, decision, or revision.

## Realization handling

Every realization note and suite is permanently non-authoritative input and is
stored only under the project-local
`evidence/non-authoritative/realizations/**` hierarchy. If an authority accepts
a claim originating in a realization, the accepted claim belongs in a
separate authoritative evidence, decision, or accepted initiative record; the
source realization is not promoted or reclassified in place. The v1.0 suite
cannot supersede authoritative evidence or accept this initiative. The example
v4 material remains non-authoritative even when used as a mandatory migration
and validation case.
