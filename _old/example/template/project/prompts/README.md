# Project-local prompts

Read and apply the canonical
[prompt keyword specification](../evidence/authoritative/LLM/11_Codex_Prompt_Keyword_Specification.md)
for ordinary requests and these prompts. It owns registered names, their
extension procedure, positional settings, list scheduling, and bounded
exception records. A setting request does not itself waive a gate or expand
the current scaffold, protected-source, lifecycle, or external-action boundary.
Preview proposals and draft receipts stay in the response; local restrictions
and independent-review obligations remain applicable alongside gate settings.

The root `../../../../../prompts` directory in a TADp scaffold is a workspace for explicit
instructions about that current project. Its `../../../../../AGENTS.md` resolves the active
scaffold from its own installed location and confines prompt-driven work to
that scaffold and any narrower boundary in the invoked prompt.

The identical files under `template/project/prompts/` are protected reusable
sources for creating this workspace. That template location is not itself an
active project-local prompt directory.

## Reference-only subject examples

The following categories illustrate suitable subject matter. They are not
instructions to execute and do not establish authority:

- **Realization preparation:** requesting creation of one project realization
  note through the applicable preparation and correlation workflow.
- **Named initiative work:** giving a direct instruction for one named project
  initiative at a workflow stage that its current evidence and state permit.
- **Authorized product work:** requesting a direct change to a project product
  when an accepted implementation initiative and every applicable entry gate
  authorize that product work.

Additional project-local prompt files may be stored below `../../../../../prompts`. They
inherit `../../../../../prompts/AGENTS.md`, remain ordinary project material under normal Git
history, and are neither authoritative evidence nor protected reusable
workflow prompts.

## Standing and gates

A project-local prompt is always a non-authoritative work description. It may
act only when applicable authoritative evidence, explicit human decisions,
initiative scope and state, correlation identity, branch, workflow stage,
protected-source rules, and verification gates permit the requested work.

Storing a prompt does not confirm an assumption, resolve a question, accept
or reopen an initiative, authorize an invariant exception,
satisfy a gate, change lifecycle state, or prove implementation, completion,
release, or cross-scaffold permission.

## What does not belong here

Do not use this directory to maintain:

- the generic TADp protocol or Codex invariant suite;
- reusable templates or their integrity locks;
- numbered initiative workflow prompts or shared workflow contracts;
- validator or protected-source semantics; or
- generic adoption, compatibility, or migration guidance.

When project work exposes a possible need in one of those areas, record or
report the need without implementing it here. Route the change to a separately
scoped protocol-maintenance instruction outside the project-local directory.

The protected numbered workflow library remains at `template/prompts/`. It is
separate from this workspace and must not be copied or duplicated here.

An actual human request to process an identified realization under adopted
specification 09 supplies its bounded intake delegation for fit-based placement,
coherent revision and necessary target/scope reopening. Capture the instruction
and each LLM-authored disposition before action. The source note or stored
prompt alone does not grant that authority. Changed claims return to Proposed
and require renewed human acceptance before delivery; other gates remain.
