## Goals and non-goals

### Goals

1. Either candidate review can define either item kind without a prior answer,
   then record each item's own sufficiently authorized same-review disposition.
2. Properly owned cross-initiative/project-wide items may receive governing
   dispositions without widening the reviewed initiative's accepted work.
3. Exact candidate bytes receive structural, link, protection, focused-scenario,
   isolated-trial and independent-review evidence before later delivery.

### Non-goals

- No standing autonomous answer authority, initiative acceptance, protected
  architecture revision or implementation of resulting work follows from a review.
- No installed-source edit, live review, example dependency, introduction,
  promotion, rollout, adoption, remote operation or release is performed here.
- No keyword, stage-number, initiative-type, narrow-scope, closed-claim or
  ordinary lifecycle revision is proposed.

## Domain model and evidence/authoritative

### Model

An item is defined separately from its disposition. A receipt preserves exact
human words or a specifically covered agent-made method/result and links every
covered stable ID and consumer. A response covers multiple IDs only when it
explicitly and unambiguously identifies the complete set and outcomes. A
handoff preserves missing authority/evidence without falsely resolving the item.

### Binding requirements

- Installed specifications 02/07/11 retain per-item human authority, exact
  receipts and specifically bounded alternative methods before reliance.
- Installed specifications 04/08 retain distinct acceptance, type-specific
  delivery, actual execution/start evidence and truthful lifecycle meanings.
- Installed specifications 05/09 retain Git, captured bases, reciprocal
  provenance, branch roles and bounded placement/reopening rules.
- Installed specifications 01/06/10/11 retain evidence precedence, narrow scope,
  conflict/coherence/closed-claim protection, interpretation and locks.
- The actual invocation authorizes the exact proposed candidate revision,
  including replacement of the named context-only restriction; it does not
  adopt that revision or waive retained gates.

[Source mapping](source-mapping.md) distinguishes installed authoritative

## Primary workflows

### Discover, define and decide either item kind

**Preconditions:** Identified review/assignment, governing evidence, original
inventory and actual canonical owners. New definition needs no preceding answer.

1. Preserve original coverage, settled items and dormant triggers; append
   independently discovered assumptions/questions with exact provenance.
2. Present one ready item at a time on the human path, preserving source options
   and clearly unaccepted recommendations. Assess other answers, including
   outside-scope answers, by authority and destination.
3. Capture a sufficient exact response in a receipt before disposition changes,
   or apply only an already recorded covered method with actual agent attribution.
   Give every new/derived item its own disposition.

**Success result:** Per-item authorized outcomes and reconciled affected records.

**Failure result:** Ambiguity, missing authority or invariant conflict preserves
exact input and unresolved state with its proper owner and recovery condition.

### Record an externally owned decision without absorbing its work

**Preconditions:** Exact target/current state, owner, governing revision, branch
and sufficient write/decision authority identified. Separate scaffold/repository/
fork/service boundaries additionally require target-naming authority.

1. Locate the other initiative's canonical register, or conditionally use the
   project register where no suitable initiative owns the item.
2. Define and record a sufficiently authorized disposition there without
   redundant approval solely for outside-initiative ownership. Otherwise retain
   an owned unresolved handoff and continue independent authorized work.
3. Link the effect/dependency to the reviewed initiative. Route independent
   resulting outcomes to Stage 0 and retain existing same-outcome revision,
   reopening, conflict and renewed-acceptance requirements.

**Success result:** Proper owner governs the item; reviewed initiative scope,
exclusions, type, ownership and acceptance claim remain bounded.

**Failure result:** No unauthorized external mutation or false resolution;
applicable unresolved dependencies still block affected handoffs.

### Report coverage and qualify the candidate

**Preconditions:** Complete original/new-item coverage and actual outcome,
handoff/dependency/re-entry evidence; actual acceptance and implementation entry
gates precede any C product execution.

1. Report answered, unresolved, deferred, transferred and blocked items by owner,
   distinguishing bounded review coverage from resolution of all external matters.
2. For this candidate run structural/link/protection checks, REV-01 through
   REV-11 scenarios and a clean pinned isolated installation/workflow trial.
3. Obtain independent complete-diff review; reconcile findings and record exact
   tested/reviewed content, manifest, compatibility, migration, recovery,
   exclusions/dependencies and remaining gates in P.

**Success result:** Truthful review coverage and actual exact candidate
qualification evidence when performed, with no wider lifecycle claim.

**Failure result:** Preserve failed checks, findings and partial outputs; resume
affected work only at its exact authority/evidence/check condition.

## Security and authorization

- **Trust boundary:** Decision target, reviewed initiative and resulting work
  retain distinct authority; separate project/fork/service boundaries remain.
- **Authentication:** Record actual responder and role/delegate; Git identity
  or a source link does not establish human authority.
- **Authorization:** Verify exact write/decision scope; preserve human defaults
  and only explicitly covered delegated IDs.
- **Secrets:** No new credential/secret flow is applicable.
- **Audit:** Retain IDs/text, exact responses, actual authorship/method/evidence/
  limits, original/capture events, receipts and Git history.
- **Data handling:** Generic isolated fixtures exclude live reviews, populated
  project history and example-fork decisions from reusable payload.

## Compatibility migration and rollout

Apply proposed behavior prospectively only after exact coherent revision and
actual adoption authority are recorded. Preserve earlier compatible revisions,
texts/options/IDs/receipts, accepted/closed claims, branch and migration identity.
Never retroactively reinterpret a review, answer an item or reopen a claim.
The project register is additive and conditional; unused projects create none.
Existing suitable registers and receipt/index sources remain canonical.

Qualification assembles a clean isolated trial from pinned baseline plus exact
C changes and declared dependencies, without hidden live P/example input.
Candidate/fixture locks may be reconciled only under covered authority after
content checks; all real installed/distribution locks stay unchanged. The
manifest retains old/new identities, transformations, exact future D/S/U
mappings, dependencies, exclusions and recovery limits. Scoped recovery preserves
subsequent work. No live cutover, backfill, introduction, adoption or rollout
occurs through this qualification slice.
